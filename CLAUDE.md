# Crema

Coffee-shop recipe-card + costing app (recipes with live cost/margin, dial-in board, printable new-hire packs). Static HTML/CSS/JS, no framework, no build step.

## Live deployment
- https://portafile.vercel.app — root rewrites to `/site/`, app at `/product/` (Vercel project `ethan16/portafile`).
- Deploy: `vercel deploy --prod --yes` from repo root. **A push to `main` ALSO deploys to production** — measured 2026-07-29, when a push meant only as a checkpoint went live within seconds (the new markup was serving before the push command's output finished). This reverses the old note here; the Vercel git integration is active now, whatever it did before. Treat any push to `main` as a deploy: run `/still-works` first and get approval for the deploy, not just the push.
- Secrets: ADMIN_KEY in Vercel prod env, local copy in gitignored `.admin-key`; Blob token in `.env.local`.
- **A PreToolUse hook now enforces the push rule**: `.claude/hooks/block-main-push.sh` (wired in `.claude/settings.json`) blocks any Claude-run `git push` that lands on `main` — explicit (`origin main`, `HEAD:main`) or bare-push-while-on-main. Feature-branch pushes pass. It only guards Claude; Ethan can still push himself with `!`. If a deploy is genuinely approved, he runs the push, or the hook gets disabled via `/hooks` for that turn.

## Gotchas
- **The product is Crema; `portafile` is still an IDENTIFIER.** Renamed 2026-07-28 (local only — see PROGRESS.md). NEVER rename the lowercase ones: localStorage keys `portafile.v1.*` / `portafile-admin-*`, headers `x-portafile-admin|owner|role|shop`, blob paths, `portafile.vercel.app`, the Vercel project, `video/portafile-launch.mp4`. Renaming a localStorage key silently erases every real café's shop — no error, just an empty app. The safe method, proved across eight steps: `sed 's/Portafile/Crema/g'` (**capital-only** — every protected identifier is lowercase), then re-grep and **count** the protected ones to prove they survived. Lowercase brand copy ("printed by portafile", the backup filename) is handled one string at a time, by hand. The historical logs (`BUILD-LOG.md`, `0[1-7]-*.md`, `handoff.md`, `RE-AUDIT.md`, safetysurface archives, `video-src/HANDOFF.md`) record the old name **on purpose** — do not rewrite them.
- **Printing is protected in code and must stay that way.** `brand/brand.css` has an `@media print` block reverting every token to ink-on-white (Ink navy is already dark enough for paper, so `--crema` and `--crema-fill` both print `#22355C`; the old gold had to darken to `#8A5A12`); `product/styles.css`'s print block is hardcoded ink-on-white and independent of the tokens. A dark palette on a product whose whole point is 4×6 cards is exactly how you mail a café black rectangles. To check one, use Playwright `emulateMedia({media:'print'})`, NOT Chrome `--print-to-pdf` (it paginates and misleads).
- **To screenshot the app headlessly, load it over `file://`** — `gate()` skips `file://`, and otherwise the access-gate scrim covers the whole page. `#printRoot` is populated but `display:none`, so waiting on it needs `{state:'attached'}`, and `Escape` does not close the app's modal.
- Root `/` is a REWRITE of /site/index.html — relative URLs in that page resolve against `/` in production and 404 (only `/assets/:file` has a rewrite). Any new script/asset reference must be absolute (`/site/...`). Bit us: `src="reveal.js"` → silent 404 at root, no animations. Bit us again, and shipped live for weeks: the FAQ's `href="privacy.html"` 404'd at `/` while the footer's absolute copy worked. Every URL on both landing pages is absolute now — `/pt` is a second rewrite with the identical hazard.
- **i18n: the English string IS the dictionary key** (`product/i18n.js`, gettext-style). No key namespace, no English dictionary, and a missing translation renders readable English instead of `undefined`. Consequences: (1) editing an English string in `app.js` silently orphans its translation — `node verify-i18n.mjs` is the ONLY thing that catches it, and it also catches duplicate keys, orphans and `%s` drift; (2) one English word needing two Portuguese words collides on one key and a duplicate JS key silently keeps only the last — disambiguate as `t('Roaster|role')`, where the `|context` suffix is stripped from the English fallback; (3) keys carry their inline `<em>`/`<strong>` markup verbatim, since the strings are interpolated as HTML.
- **Language lives in `S.shop.lang`, so it SYNCS** — the owner sets it once and staff devices follow on the next poll. `applyLang()` runs at the top of `render()` for exactly that reason (`syncPull` can replace `S` wholesale). Default is `detectLang()` off `navigator.languages`, so a Lisbon browser gets Portuguese with no action and Playwright (en-US) always gets English — which is why every existing suite still passes. Switching language deliberately does NOT retranslate the shop's own recipes; "Reset to demo" reseeds in the current language.
- **Currency follows language** (en→USD, pt→EUR) via one `Intl.NumberFormat` in `money()`. Deliberate: it covers both real cases with one setting. Splitting `S.shop.currency` out is the upgrade path if a pt-BR or euro-priced English shop ever appears — not before. `Intl` emits a NON-BREAKING space in "1,22 €", so match `/\d,\d\d\s*€/`, never a literal space.
- **There are TWO demo seeds** (`seedEN`/`seedPT`), and the Portuguese one is a different *menu*, not a translation: galão, meia de leite, pingado, abatanado at Lisbon prices, in ml and °C. Traditional drinks carry `Louça (lavagem)` (€0.02 dishwashing) instead of a paper cup, because in Portugal a café is drunk at the counter in porcelain — cost the paper cup in and every espresso reads as a loss at €1.00. Both seeds are hand-written, so the likeliest bug is a recipe naming an ingredient that isn't in the list: `I[name]` yields `undefined`, the item silently costs nothing, and nothing throws. `?selftest=1` asserts every item in BOTH seeds resolves.
- **Adding a language means editing `api/metrics.js`.** Its `DEMOS` array is a hard-coded copy of every seed's name + recipe/ingredient counts. A seed that isn't listed there makes every shop in that language read as "customised" the instant it opens — silent 100% adoption, no error. `node verify-metrics.mjs` covers both seeds.
- Signup role `<option value>`s stay English while the labels translate: the value is POSTed to `/api/lead` and counted in the founder metrics, so translating it would split "Owner"/"Proprietário" into two buckets.
- `product/index.html` ships English markup; `applyChrome()` retranslates the tabs, title, tooltips and `<html lang>` on every render so the picker works without a reload. Adding a tab means adding it to the `TABS` map there.
- Dial-in numbers render through `dec()`, which formats only genuinely finite values and passes anything else through untouched — dial-in values are user-entered and are NOT guaranteed numeric (see the `esc()` gotcha below). Always `esc(dec(x))`, never `dec(esc(x))`.
- **The landing pages diverged once and no test noticed for days.** The 2026-08-01 redesign moved `/` to `v2.css` and left `/pt` on `site.css`, while `verify-site.js` asserted one shared sheet — so it was testing a file the English page no longer loaded, and would have passed with `v2.css` 404'd. Both pages are back on `v2.css` since 2026-08-23. The guards stay, because ONE sheet is not the same as one assertion: `verify-site.js` asserts each page's own `href` and resulting background, and `health_check.py` probes the sheet AND that `/pt` still links it. A page whose stylesheet 404s renders fully-worded but completely unstyled, which a body-text check passes happily. The English string baked into `v2.css` is the mock card's `content:"4×6 · PRINTS CLEAN"`, overridden by `html[lang="pt-PT"] .mockcard::after` — **any new CSS `content:` string needs that override or it ships English onto the Portuguese page.**
- CSP (vercel.json) blocks ALL inline `<script>` — page JS must be external same-origin files. Inline `style=` attrs are allowed.
- `.vercelignore` publishes ONLY site/product/video — adding a new top-level dir won't deploy without editing it.
- Zero external requests by design: system fonts only, no CDNs; keep it that way.
- CORS: vercel.json pins `Access-Control-Allow-Origin` to the prod origin on everything EXCEPT `/api/` — `api/lead.js` must keep `*` or the localhost:4322 dashboard's "Fetch signups" breaks.
- Site scroll-reveal: hiding styles are gated behind a JS-added `.js` class at zero specificity (`:where()`) — don't raise their specificity or components lose their transforms (see ~/.ai/patterns/scroll-reveal-static-site.md).
- Headless-Chrome screenshot verification: old headless clamps width to ~500px (fake mobile overflow — test narrow widths via iframe) and virtual-time freezes transitions (blank reveals — use `--headless=new` or `--force-prefers-reduced-motion`).
- Access gate (`gate()`) is lead capture, not auth — no password, no verification, it only unlocks one browser. It skips `file://`, webdriver browsers (so verify suites pass it), anyone who already filled it in, and **anyone arriving on a `?k=` staff link**. That last one is load-bearing: staff devices synced fine but the form sat on top of the loaded shop, so baristas closed the link and reported sharing as broken. Never gate a share link — and the leads it captured from staff were junk (guessed shop name, no shopId linkage; only owners get `lead.linked`).
- Sync writes carry a `ts` stamp; `api/state.js` 409s any PUT older than the stored blob (client reacts by pulling). Clients never push before their first successful pull — protects a real cloud copy from a freshly-reseeded browser. Before overwriting local state, the client snapshots it to `portafile.v1.presync`.
- Three-part key model: data lives at `shops/<shopId>.json`, reached only via pointer `keys/<shareKey>.json` (the `?k=` link, rotatable); `owners/<shopId>.json` holds a sha256 of the owner token (`x-portafile-owner` header, localStorage `portafile.v1.owner` — never in a URL). A 404 on an unknown key must CREATE NOTHING — the client only seeds the cloud when it holds an owner token; that rule is what makes "Reset staff link" real revocation. Legacy shop `187cdea…` has a pointer (same string as its shopId) but deliberately NO owners/ record — its link can't rotate, per Ethan.
- Revoking is a HARD kill: a staff device told **410 revoked** wipes its `portafile.v1*` keys (except `lead*`), sets `portafile.v1.revoked`, and shows a lock screen that survives reload; opening a different working link clears it. Four guards make that safe — do not remove any: (1) ONLY 410 wipes, never a 404; (2) two 410s are required, since one read can flake; (3) it only fires when `portafile.v1.synced` equals the current key, so clicking a stale link can't destroy a stranger's own local shop; (4) owner-token devices are never wiped; whether a device counts as "owner" on a 410 is decided by the SERVER (the 410 body's `owner` flag, hash-checked against THAT shop) — the local token alone proves nothing, since it may belong to a different shop (that bug made such devices unrevokable, retrying forever). Confirmed owners settle-and-retry; everyone else locks.
- **Vercel Blob is eventually consistent — never build an authorization check on a read.** Measured, not assumed: back-to-back reads of the same existing path returned found then null; reads after an overwrite returned the PREVIOUS value for up to several seconds; `list()` lags both writes and deletes. So: (1) revocation is a VALUE comparison, never a missing blob — pointers are never deleted, a link is dead when `k !== owners.currentKey`, answered as **410 revoked**; (2) a 404 never means revoked (a flaky read produces one), so the client only wipes on 410, and only after TWO of them; (3) the one place absence would grant authority — claiming a shopId — uses `put(..., {allowOverwrite:false})`, the store's only atomic check, instead of read-then-write; (4) use `get(path,{access:'private',useCache:false})` and `del(path)` by pathname, never `list()`, for exact-path work. Consequence to state honestly: revocation takes a few seconds to take effect, which is fine for firing a barista and is NOT a strong real-time guarantee.
- Rotate order is: write the new pointer, then flip `owners.currentKey`. That flip IS the revocation, so a half-failure leaves the old link working and returns an error, rather than telling the owner a live link is dead. Owner devices never wipe or lock and get a settle-and-retry on 410; a rotate also pauses the owner's own sync ~2.5s so the consistency window can't look like a lockout.
- The revocation wipe clears every `portafile.v1*` key EXCEPT `portafile.v1.lead*` — the signup record is not a credential. Tested.
- **Deleting a shop's cloud data** (`DELETE /api/state`, admin-key header, shopId in `x-portafile-shop`; dashboard button): writes the `owners/<shop>.json` **tombstone FIRST**, then `del`s `shops/<shop>.json` twice around a 1200ms sleep. Order is load-bearing — delete-then-tombstone lets an in-flight owner PUT resurrect the data through Blob's lag. Every GET/PUT/rotate path then answers **410 deleted** with the same server-decided `owner` flag revocation uses. Client: **every** device wipes all `portafile.v1*` **including `lead*`** (opposite of revocation — deliberate, so the signup gate returns), the owner's device included. Owner devices used to keep their local `portafile.v1` so the button could never destroy a shop's only copy; that left the returning signup form sitting on top of a live shop with the owner's own custom drinks still on screen, which reads as "the delete did nothing" (Ethan hit it in testing 2026-07-24 and called it a bug). Delete now means clean slate everywhere — back to the demo seed — so it IS the one button that can erase a café's last copy, and the dashboard confirm says exactly that. Tombstones are never removed, so the shopId stays permanently dead.
- **"Is this dead shop mine?" must be answerable WITHOUT the server.** The 410 `deleted` body carries the dead `shopId`, and the client compares it to `portafile.v1.shopid`. Both older proofs fail together in the commonest case: `portafile.v1.synced` is only written after a first 200 GET (a device that SEEDED a shop has none for ~30s), and the server's `owner` flag comes from the tombstone's `ownerHash`, copied from a read that can flake to null — and a pre-owner-token shop never had one. With neither, the delete fell into the stale-bookmark branch: sync stopped silently, the app stayed open, the gate never returned (what Ethan saw), and the same missing flag would have let the founder's button wipe an owner's only local copy. Disclosing the shopId is safe only because it is disclosed only for a tombstoned shop; it is a response body, never a URL.
- **The poll interval is a COST decision, and the poll is not a guarantee.** `POLL_MS` in `product/app.js` is **5 minutes**, not the 30s it was until Sep 2026. Every `GET /api/state` costs 3-4 Blob reads and Vercel's free tier allows **2,000 advanced Blob operations a month** — at 30s, one tab left open burned the entire month in about four hours (the 75%-of-quota warning that prompted the change). The timer is not what makes sync feel live; the two listeners below are. Raising it back means paying for Blob. Browsers also freeze timers in background tabs, so it was never a promise anyway. The client re-pulls on `visibilitychange`→visible and on `online`, so a delete or revoke lands when the tab is next looked at (measured live: 24s → 4s). Guarded by `if (!syncPushT)` so a focus-pull can't overwrite an edit still inside its 800ms save debounce; `syncPush` zeroes `syncPushT` when it fires to make that guard real. A local-only browser (never synced, or gone local after an earlier delete) can never be reached at all — that is a property of a no-accounts product, not a bug.
- Playwright `addInitScript` re-runs on EVERY navigation — any test whose subject calls `location.replace()` after wiping localStorage will have its seed silently restored. `verify-sync.js` guards seeds behind a `pf-test-stopseed` flag (named outside the `portafile.v1` prefix so wipes don't clear it).
- **Founder metrics (`api/metrics.js`): anything read out of a shop's DATA is aggregate-only, and that is a published promise.** `site/privacy.html` says we never read individual recipes/costs, but do count feature usage across all shops together and do record which dates each shop used the app. So the GET (admin key) reads shop states INSIDE the function and returns only counts and percentages from them — never a per-shop recipe, price, adoption boolean, or the shop name **as stored in their synced state**. The `perShop` rows (levels 2–3) are the narrow exception and carry METADATA only: the name/email the owner typed into the signup form (from the lead record — they gave that to Ethan directly), `owners.created`, the shop blob's `uploadedAt`, and a count of active dates. Moving anything across that line makes the live privacy page false. Adoption is inferred from data the app already stores (renamed shop / recipe+ingredient counts vs the demo seed, sign-offs or a second barista, a 4th dial-in); print usage is deliberately NOT measured because nothing records it and doing so means writing usage counters into customers' own data. `list()` is used here only to ENUMERATE (its index lags by seconds — fine for counts, still never for resolving a known path).
- **Usage dates (`activity/<shopId>.json`) are stamped by `api/state.js`, never by the client.** Both GET and PUT stamp — staff devices mostly READ cards, so a PUT-only stamp would miss the usage that matters — but only after the request is authorized and answered, never for `revoked`/`deleted`/`unknown`. The whole thing is `try/catch`-swallowed bookkeeping: it must never change a status code or block a save. A warm-instance `Map` (same trick as the `HITS` rate limiter) keeps a 30s poll from costing a Blob read every time — one read + at most one write per shop per day per instance. Dates are UTC (a late California close counts as the next day) and the log is trimmed to 60 entries. It lives in its OWN blob because the shop state syncs down to customer devices, and the founder's DELETE path `del`s it — otherwise an erased shop keeps showing usage.
- **Time-to-onboarding must start from the EARLIEST lead record for an email.** When a browser links its shopId, `product/app.js` re-POSTs the whole lead and `api/lead.js` stamps a FRESH server `ts` — a second record for the same person. Measuring from it reports onboarding times near zero. `onboarding()` in `api/metrics.js` is exported and pure for exactly this reason; `verify-metrics.mjs` fails if the rule is broken.
- Feedback (`POST /api/metrics`, from the app's **? → Send feedback**) is a public unauthenticated write, guarded the same way as `api/lead.js`: honeypot field, per-instance IP rate limit, length caps, one blob per submission. It carries sentiment, an optional note and email, and the sender's role — never anything from the shop's data.
- **The verify suites can't pollute production, but a human hand-testing it can.** `app.js` skips both the lead POST and the shopId-linking re-POST when `navigator.webdriver` is true, so Playwright never writes to the founder's store — that guard does nothing for a real browser on portafile.vercel.app with fixture values pasted into localStorage, which is exactly what live-verifying the delete/sync flows looks like. Such a run writes a REAL `leads/` blob. `api/lead.js` stores no IP and no user-agent by design, so a mystery signup can only be attributed by forensics: the fixture strings (`o@y.z`, `'c'.repeat(40)` etc. from `verify-sync.js`) and the record's `ts` against `git log`. Keep test fixtures obviously fake for that reason — a plausible email and café name would be indistinguishable from a real first customer. Clean up with `curl -X DELETE -H "x-portafile-admin: $(tr -d '\n' < .admin-key)" "…/api/lead?ts=<ts>"` and confirm with several reads (the blob index lags deletes).
- Health check (`health_check.py`, daily 15:00 UTC): probes the live site with no credentials and mails the operator the result **every run, pass or fail** — a daily all-clear, so a missing email is itself the alarm (the workflow stopped running). Its `api/state?k=0*40` → 404 `unknown-key` case is the canary for BOTH the serverless function and the private Blob read path (a dead store 500s instead). It also asserts `admin/dashboard.html` 404s — that no-auth dashboard must never deploy. Failing checks retry once after 20s before alarming (a single blip is not an outage). Run it on demand with `gh workflow run health.yml` (every run emails, so there is no force-send flag); if you change a page's copy, update the expected marker strings in CHECKS or you get a false alarm.
- **Never run `npx playwright ...` casually.** `verify-sync.js` and `verify-gate.js` `require()` Playwright by absolute path out of the shared npx cache (`~/.npm/_npx/e41f203b7505f1fb/…`). Any bare `npx playwright` command silently UPGRADES that cache to a version whose browser build isn't installed, and both suites then die with "Executable doesn't exist" — looking like a broken test, not a broken toolchain. Fix: `npx playwright install chromium`. To drive a browser ad hoc without touching the cache, launch with `{ channel: 'chrome' }` and use system Chrome.
- **To exercise a rate limiter without writing junk into the founder's store**, send requests that fail validation *after* the limiter runs: `POST /api/lead` with an invalid email, or `POST /api/metrics` with no sentiment — both return 422, increment the counter, and write no blob. The honeypot path returns *before* the limiter, so it can't be used to test one. (Verified live 2026-07-25: 12 POSTs → 8×422 then 429, store still 0/0/0 afterwards.)
- **`verify-sync.js` does NOT test `api/state.js`** — it `route()`s `**/api/state*` to a JS *mirror* of the server logic written inside the test file. It can be fully green while the real handler is broken, and for a long time no API code had any coverage at all. `verify-api.mjs` (root, `node verify-api.mjs`) is the one that executes the real handlers: it swaps `@vercel/blob` for an in-memory store via `module.registerHooks` and calls `state.js`/`lead.js`/`metrics.js` with fake req/res. No network, no keys, writes nothing. Its blob stub is deliberately *not* eventually consistent — it tests authorization logic, not consistency windows.
- **Reads and writes need separate rate-limit budgets.** `rateLimited(ip, store, max)` takes the bucket: writes use `HITS`/120, `GET /api/state` uses `GET_HITS`/600. Reads are the *polling* path — every device re-pulls on the `POLL_MS` timer and on every focus, **and a whole café's devices share one public IP behind the shop wifi**. The 600 was sized against the old 30s poll (~20/10min per device, so six devices ≈ 120 before anyone edits); at 5 minutes the steady-state figure is ~2 per device and the margin only grew, so the number stays as-is. Reusing the write budget would throttle a busy real shop. Verified live: 600 sequential keep-alive GETs → 429 at the budget, which also proves `clientIp()` resolves on Vercel (a blank IP silently disables the limiter entirely).
- **Load-testing the GET limiter from your own machine makes `health_check.py` cry wolf.** Its `?k=0×40` canary answers **429 instead of 404** for up to 10 minutes afterwards and the check reports a false outage. The daily GitHub run makes one request from a fresh runner IP, so it can never trip it — but wait out the window before believing a local run.
- **The admin key is a header on all four admin routes** (`x-portafile-admin`), never `?admin=` — query strings land in access logs. Adding that header made the dashboard's fetches **preflighted**: the browser sends `OPTIONS` first, and `api/lead.js`/`api/metrics.js` must list the header in `Access-Control-Allow-Headers` or the real request is never sent — it fails as `net::ERR_FAILED`, *not* a 401, which reads like the site is down rather than like an auth problem. So `admin/dashboard.html` and both functions must deploy together. (`vercel.json` sets no `Allow-Headers` of its own and its ACAO pin excludes `api/`, so the functions own their CORS.)
- **The launch film is a marketing asset that goes stale silently.** Its narration is `say -v Samantha -r 172` (see `video-src/narration.sh`) and it still claims "No server" — false since sync shipped 2026-07-17. It is also English-only: the `/pt` page links it labelled "(em inglês)", which is honest but not a translation — a re-cut would need a Portuguese narration voice (`say -v Joana`), and `say` silently falls back to the default on an unknown voice name, so md5 the output against a fake name before believing it worked. Any change that makes an existing promise false must be chased into the video too, not just `site/`. Re-cutting is possible only because the source assets were rescued into `video-src/` from a scratch dir; the original ffmpeg assembly command was NOT saved and must be rewritten (recipe described in `06-launch-video.md`). Two traps: `say` **never errors on an unknown voice** — it silently uses the default (proven by md5-identical output for a fake name), and macOS 26 removed the Manage Voices download UI, so no better local TTS voice exists. Full context: `video-src/HANDOFF.md`. If the film's length changes, update the "75-second film" string at `site/index.html:193`.
- **A deliberate language switch reseeds the demo menu — but only on an untouched demo.** `langSel.onchange` calls `pristineDemo(from)` BEFORE mutating anything; if the shop still matches that language's seed exactly it becomes `seed(to)` (keeping only `S.tab`). Rationale: an American menu priced in euros behind a Portuguese UI reads as a broken translation, and there is nothing of the owner's to protect yet. Any owner work vetoes it forever. Two traps live here: (1) **`demoSig()` must strip ids and timestamps** — `seed()` mints fresh `uid()`s and `Date.now()` dial-in stamps every call, so a plain `JSON.stringify` comparison never matches; (2) **whatever you strip, you go blind to.** Recipe items were fingerprinted by `qty` alone because `item.ing` is one of those random ids — so swapping whole milk for oat milk at the same qty read as untouched and the switch destroyed that edit. It now resolves `id → ingredient name` first. When a comparison strips ids to work at all, write down what else went with them. **Corollary: any NEW user-editable field must be added to `demoSig()` in the same commit**, or a shop whose only work is in that field reads as pristine and the switch deletes it (path step descriptions, added 2026-07-27, are in there for exactly this reason).
- **`matchesADemoSeed` (`api/metrics.js`) must NEVER be reused for anything that replaces data.** It compares only shop name + recipe/ingredient counts and ignores dial-ins, baristas and sign-offs — fine for classifying a shop on the dashboard, where being wrong skews a number. Reused for the language swap it would have silently destroyed a café's week of real dial-ins. Same question, different consequence, different threshold — keep the two tests separate.
- **A private window makes hand-testing worse, not safer.** The `navigator.webdriver` guard means no verify suite ever writes to the founder's store, but a human in a normal window meets the real gate, and a human in a *private* window has no saved `lead*` record suppressing it — so **every private-tab test is a fresh signup**. Two landed on 2026-07-26 ("Portugal", "Portugalll"), one of them under Ethan's second address, so "is it my email?" is not a reliable filter; attribute by `ts` against `git log`. Adding `?k=` to the URL avoids the gate entirely and is the safe way to hand-test.
- **Dial-in values are only numbers when typed locally** (`parseFloat`); nothing coerces them when state arrives from the cloud or an import, and `validBackup()` only checks `Array.isArray(s.dialins)`. Every *render* site must therefore `esc()` them — the board, the history table, and the new-hire print pack. The 2026-07-25 audit named only the board; the other two were the same live bug. Fixing the sink named in a finding is not the same as fixing the finding.
- **The training path renders in `pathOrder()` order, not array order** — day ascending, then array position within the day, because the printed pack groups by day (`viewPrint` 'hire') and a screen in raw array order disagrees with the paper the moment a step moves days. It returns INDICES and mutates nothing, so synced and legacy shops need no migration. Consequences: `↑↓` swap the DISPLAY neighbour and only within one day (disabled at a boundary, re-checked in the handler); a step moved to another day joins that day at its HEAD, since the tiebreak is array position; and both the path column and the Sign-offs checklist must iterate `order`, never `S.path`, or the two columns disagree.
- **`.pathlist input.note` saves on blur WITHOUT `render()`** — re-rendering would drop focus when the owner tabs down the list — so the handler must hand-patch every other view of `p.note` itself. Today that is the Sign-offs cell (`textContent`, never `innerHTML`). This shipped stale for exactly one session: the description appeared in the path editor and nowhere else until an unrelated click re-rendered. **A second view of a field means revisiting every handler that writes it.** The day input is the opposite case and DOES `render()`, because changing a day re-sorts the list — that is the point. Note `.note` is also the dial-in log's class, so both the CSS and the wiring stay scoped to `.pathlist`.
- **Staff (`?k=` link) get the training path read-only** — no `↑↓×`, no add-step row, no editable day or description, same `staffView()` predicate as the Margin Report. This one IS visibility-only, not a security boundary — the training path itself has nothing to hide.
- **Ingredient costs ARE now a real security boundary, not just a hidden UI element.** `api/state.js` splits `costs/<shopId>.json` (real `unitCost` values, populated and read back only for a request that proves ownership) from `shops/<shopId>.json` (never carries a real cost, regardless of who wrote it — `stripCosts()` runs on every PUT). A staff device's synced copy genuinely never contains real numbers now; opening devtools on a staff link shows zeros, closing the gap this file used to document as an accepted limitation. The one danger a naive version of this would hit: the client PUTs its WHOLE local state on every save, staff devices included, and a staff device's local ingredients read `unitCost:0` (never having received real numbers) — an unguarded write would let a staff autosave null out the owner's real prices. Fixed by never writing `costs/` except when the request proves ownership (`role === 'owner'`); a staff PUT still writes cleanly to `shops/` but touches `costs/` not at all. Covered in `verify-api.mjs` (the real handler, not the `verify-sync.js` mirror) — including the exact staff-autosave-can't-erase-costs regression. Migrated and deployed 2026-08-11 (`migrate-costs.mjs`, one-time, already run).
